# RGW C++ 到 C 转换项目概要设计文档

## 1. 项目概述

### 1.1 目标
将 Ceph RGW (RADOS Gateway) 模块从 C++ 语言逐步转换为 C 语言，同时保持功能完整性和性能指标。转换后的代码应具备更好的可移植性、更小的运行时依赖，并能在资源受限环境中运行。

### 1.2 范围
- **转换范围**: `src/rgw/` 目录下的核心代码（约 560 个文件，30 万行代码），第三方C++库制定转换方案，尽量采用成熟的替代方案。

- **基础设施**: 完善 `c_common` C 容器库，提供 STL 等效功能

### 1.3 核心原则
1. **渐进式转换**: 分阶段实施，每阶段可独立测试和回滚
2. **双向兼容**: 转换过程中保持 C++ 与 C 代码共存，支持混合调用
3. **测试驱动**: 每一步转换都需通过自动化测试验证
4. **性能保障**: 关键路径性能不低于原版的 90%

## 2. 整体转换策略

### 2.1 渐进式转换路线图
采用自底向上、从内向外的转换顺序：

1. **阶段 0 - 基础设施准备** 
   - 完善 `c_common` 容器库，补充缺失容器
   - 建立 C 语言面向对象框架
   - 制定编码规范和错误处理机制

2. **阶段 1 - 核心数据类型转换** 
   - 转换基础数据类型（字符串、XML、Base64 等）
   - 替换 STL 容器为 `c_common` 等效实现
   - 建立混合编译环境

3. **阶段 2 - 存储抽象层转换**
   - 转换 SAL (Storage Abstraction Layer) 接口
   - 转换 RADOS 驱动和其他存储驱动
   - 实现 C 语言多态机制

4. **阶段 3 - REST 核心转换**
   - 转换操作处理器 (`rgw_op.cc`)
   - 转换 REST 框架 (`rgw_rest_*.cc`)
   - 转换 S3/Swift 协议实现

5. **阶段 4 - 上层模块转换**
   - 转换认证授权模块
   - 转换服务层和前端网络
   - 转换异步协程框架

6. **阶段 5 - 优化与收尾**
   - 性能优化和内存泄漏修复
   - 文档完善和最终验收

**总周期**: 54-72 周

### 2.2 代码共存策略
- **混合编译**: 使用 C++ 编译器编译混合代码，C 代码通过 `extern "C"` 封装
- **接口适配层**: 为每个转换的模块提供双向接口适配
- **条件编译**: 使用 `#ifdef __cplusplus` 支持两种语言调用
- **渐进替换**: 逐个文件转换，转换完成后立即测试

### 3.2 面向对象模拟框架
```c
// 虚函数表模式
typedef struct rgw_object_vtable {
    int (*method1)(struct rgw_object* obj, ...);
    void (*method2)(struct rgw_object* obj, ...);
    void (*destroy)(struct rgw_object* obj);
} rgw_object_vtable;

typedef struct rgw_object {
    rgw_object_vtable* vtable;
    // 实例数据
} rgw_object;

// 使用示例
int rgw_object_call(rgw_object* obj) {
    return obj->vtable->method1(obj, ...);
}
```

### 3.3 错误处理机制
- **统一错误码**: 定义项目级错误码枚举
- **错误传播**: 使用返回值传递错误，禁止使用 `setjmp`/`longjmp`
- **错误上下文**: 可选错误信息附加，便于调试
- **资源清理**: 使用 `goto cleanup` 模式确保资源释放

### 3.4 内存管理方案
- **引用计数**: 对需要共享所有权的对象实现引用计数
- **内存池**: 高频分配对象使用内存池优化
- **自动化检测**: 集成 AddressSanitizer、Valgrind 到 CI
- **RAII 模拟**: 使用 `rgw_auto_free_t` 等包装器实现作用域内自动释放

## 4. 关键技术方案

### 4.1 C++ 特性转换方案

| C++ 特性 | 转换方案 | 注意事项 |
|----------|----------|----------|
| 模板 | 类型擦除（`void*` + 操作函数表） | 对常用类型组合提供特化版本 |
| 异常 | 错误码返回 + 错误上下文 | 严格检查所有返回值 |
| 虚函数 | 函数指针表（vtable） | 初始化时填充 vtable |
| 智能指针 | 手动管理 + 引用计数包装 | `unique_ptr` → 手动管理，`shared_ptr` → 引用计数 |
| Lambda 表达式 | 函数指针 + 上下文参数 | 上下文需手动管理生命周期 |
| 命名空间 | 前缀命名（如 `rgw_`） | 避免名称冲突 |
| RTTI | 手动类型标签 + 转换函数 | 添加 `type_id` 字段到基类 |
| STL 算法 | 重新实现为通用函数 | 提供常用算法（排序、查找等） |
| 并发原语 | 使用 pthread 或 C11 线程 | 封装为统一接口 |

### 4.2 混合编译与链接
```
// C++ 调用 C
extern "C" {
    #include "rgw_core.h"
}

// C 调用 C++
// 通过包装函数，在 C++ 源文件中实现
#ifdef __cplusplus
extern "C" {
#endif
    int rgw_cpp_wrapper_function(...);
#ifdef __cplusplus
}
#endif
```

**构建系统调整**:
- 修改 CMakeLists.txt 支持 C 和 C++ 混合编译
- 为转换模块添加条件编译选项
- 保持向后兼容，确保未转换模块正常编译

### 4.3 第三方库处理策略
1. **保留 C++ 包装**: jwt-cpp、picojson 等小型库，创建 C 包装层
2. **替换为 C 版本**: 寻找功能等效的 C 库（如 json-c 替代 picojson）
3. **重新实现**: 对关键且无替代的库进行简化 C 实现
4. **直接使用**: librados C 客户端可直接使用

## 5. 模块转换顺序与依赖

### 5.1 模块依赖关系
```
基础容器 (c_common)
     ↓
核心数据类型 (rgw_string, rgw_xml, rgw_b64)
     ↓
错误处理框架
     ↓
存储抽象层 (SAL) 接口
     ├── RADOS 驱动
     ├── DBStore 驱动
     └── POSIX 驱动
     ↓
REST 核心框架
     ├── S3 协议实现
     ├── Swift 协议实现
     └── 其他协议
     ↓
认证授权模块
     ↓
服务层与前端
```

### 5.2 转换优先级
1. **P0 (基础依赖)**: c_common 容器、核心数据类型、错误处理
2. **P1 (核心模块)**: SAL 接口、RADOS 驱动、REST 框架基础
3. **P2 (协议实现)**: S3 协议、Swift 协议、认证授权
4. **P3 (上层模块)**: 服务层、前端网络、异步协程
5. **P4 (优化完善)**: 性能优化、工具链、文档

## 6. 测试与质量保障

### 6.1 测试策略
- **单元测试**: 每个转换后的 C 模块必须有单元测试，覆盖率 >90%
- **集成测试**: 验证 C/C++ 混合调用正确性
- **回归测试**: 确保功能与原始 C++ 版本一致
- **性能测试**: 关键路径性能不低于原版 90%
- **压力测试**: 内存、并发压力测试，确保无泄漏

### 6.2 回滚机制
1. **版本控制**: 每个转换阶段创建独立分支
2. **快速回滚**: 任一测试失败可立即回滚到上一稳定版本
3. **A/B 测试**: 并行运行转换前后版本，对比结果
4. **监控告警**: 生产环境灰度发布，实时监控异常

### 6.3 质量门禁
- **编译警告**: 零警告编译（-Wall -Wextra -Werror）
- **静态分析**: 使用 Clang Static Analyzer、Coverity 定期扫描
- **动态分析**: Valgrind、AddressSanitizer 内存检查
- **代码审查**: 所有转换代码必须经过 peer review
